# Apex 2.1.0

A cleanup and hardening release: the app is lighter and faster to migrate, onboarding tours read correctly in Arabic, and document approvals are safer.

## What changed for users

- **Safer approvals.** Submitting or cancelling a governed document now always re-checks your authorization, closing a path that could skip the approval workflow.
- **Steadier document workflows.** Statuses can no longer be edited by hand outside the approval flow, rejected requests can be revised or reopened instead of dead-ending, and an approved damage write-off can be cancelled.
- **One clearer home.** The two old kernel landing pages are folded into a single Habitat home with setup, roles, and logs within reach; back-office record types are tucked out of the everyday workspaces.
- **Onboarding tours read correctly in Arabic.** Every guided tour positions its steps neutrally, so right-to-left layouts are no longer misaligned.
- **A cleaner, faster app.** A large amount of dead and legacy scaffolding was retired, so sites migrate faster with no change to your data.

## What changed under the hood

- Retired the `apex_habitat` compatibility bridge and 33 spent one-time migration patches; the app installs and migrates against a single clean baseline.
- Roles are now provisioned entirely by idempotent Python setup (no role fixtures), keeping first-install and update behavior consistent.
- Removed the unused Employee Deduction Acknowledgment record and its dead workflow.
- Deleted dead frontend components and empty module directories, and tightened the permission-parity guard.

## If you are updating an existing site

1. Run `bench --site <site> migrate`.
2. Run `bench build --app apex`.
3. Clear the site's cache before operators continue.

## Correction — 2026-07-26

The published note above is kept as it shipped. This corrects one claim in it, and adds a prerequisite to the update steps.

- **A site installed under the old package name cannot simply be migrated.** "Installs and migrates against a single clean baseline" holds for a new site, and for a site already carrying the current application identity. It does not hold for a site first installed while the application shipped under the name `apex_habitat`: on those the migration stops with `Could not find app "apex_habitat"`, and the site stops serving until the stored identity is corrected.
- **There is no automatic repair, and there cannot be one.** A site looks for its updates under the application name it was installed with, so an update published under the new name is never opened by a site still holding the old one. The corrected name has to be put in place from outside the update.
- **The real prerequisite is the app-identity upgrade.** Before updating such a site, plan a maintenance window and follow the published upgrade runbook for the application identity: back up, correct the bench application registry, run the identity cutover, then migrate. Its steps are individually proven, but the whole sequence has not yet been carried out against a live site — walk it once on a scratch site before a real one.
