# Patch register policy (audit 2026-07-25):
#   PERMANENT      = idempotent seeder. Must keep replaying on migrate so a site
#                    installed earlier picks up records added to the seed later.
#                    (Fresh installs never run patches; they seed via after_install.)
#   STILL-REQUIRED = one-time rename / cleanup / backfill whose "every deployed site
#                    has already run it" gate CANNOT be answered from source. Prune
#                    against a real tabPatch Log census, or on an owner decision that
#                    accepts the risk in writing — on 2026-08-02 four pre-v2 one-time
#                    backfills went that way (scheduled-task template migration,
#                    building address, assignment supervisor, deduction policy), with
#                    the two Masar token patches deliberately kept because a site that
#                    never ran them keeps a personal token readable and never-expiring.
#   Every entry below carries its own reason.
#   Earlier passes pruned 53 spent one-time patches (2026-06-03 and 2026-07-23).
#
#   A patch module on disk that is deliberately NOT registered here must say so in
#   its OWN docstring, with two labelled lines carrying real reasons:
#       UNREGISTERED-PATCH: <why registering it would be wrong>
#       COVERED-BY:         <what provides that state instead>
#   Currently one, recorded in this file:
#     v2_0.app_identity_cutover — the apex_habitat -> apex upgrade path. It CANNOT be
#       registered: frappe resolves patches per installed-app name (patch_handler.py
#       get_all_patches -> get_app_path(app, "patches.txt")), and a pre-rename site's
#       name is still the dead package, so it never opens this file. Registering it
#       would reach only already-canonical sites and sweep every table for nothing.
#       Operator-invoked instead, per docs/administration/identity-upgrade.md.

# The demo seeders that used to sit in v1_x are no longer shipped: demo data is not part
# of the product, and a customer install has no use for a module that fabricates users and
# trips. They were never wired here — a normal `bench migrate` must never create
# demo data — and they now live only in the maintainer's own tree.
#
# HISTORICAL (security), and STILL ACTIONABLE even though the module has left this
# repository: seed_demo_role_logins once carried the demo login password as a source
# literal, so every checkout shared one working password. The literal is gone from the tree
# but REMAINS IN GIT HISTORY, so it must be treated as burned. Deleting the module does not
# retire the accounts it may already have created.
#
# NOT ANSWERABLE FROM SOURCE: whether any real site ever created those two accounts. The
# seeder only wrote Users when developer_mode was on, and it was never an active entry
# here, so it can only have run by an explicit bench execute or by a migrate predating
# that un-wiring.
#
# OPERATOR ACTION, per site, in this order:
#   1. tabPatch Log for apex.patches.v1_x.seed_demo_role_logins — a row means a migrate
#      reached the module while it was still registered. It does NOT mean Users were
#      created: the developer_mode gate may have returned first. Absence of a row is
#      likewise not an all-clear, since a manual bench execute logs nothing.
#   2. tabUser for supervisor.demo@example.com and employee.demo@example.com — this is the
#      decisive check, and it is named here rather than in the module because the module is
#      gone. Present means the published password is live on that site: disable or reset.
# Until step 2 is done on a given site, those accounts are UNKNOWN, not safe.
