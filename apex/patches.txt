# Patch register policy (audit 2026-07-25):
#   PERMANENT      = idempotent seeder. Must keep replaying on migrate so a site
#                    installed earlier picks up records added to the seed later.
#                    (Fresh installs never run patches; they seed via after_install.)
#   STILL-REQUIRED = one-time rename / cleanup / backfill whose "every deployed site
#                    has already run it" gate CANNOT be answered from source. Prune
#                    only against a real tabPatch Log census, never on assumption.
#   Every entry below carries its own reason.
#   Earlier passes pruned 53 spent one-time patches (2026-06-03 and 2026-07-23).
#
#   A patch module on disk that is deliberately NOT registered here must say so in
#   its OWN docstring, with two labelled lines carrying real reasons:
#       UNREGISTERED-PATCH: <why registering it would be wrong>
#       COVERED-BY:         <what provides that state instead>
#   tests/test_patch_registration_guard.py fails the build on any patch module that
#   is neither registered below nor carries both markers, and caps how many such
#   documented exceptions may exist. Currently four, all recorded in this file:
#     v1_0.seed_salis_operations_roles — execute() is an unconditional `return`, so
#       registering it is indistinguishable from not registering it. The module stays
#       on disk because salis/setup.py imports it.
#     v1_x.seed_masar_demo_movement, v1_x.seed_demo_role_logins — demo seeders; see
#       the A-070 note in [post_model_sync] below.
#     v2_0.app_identity_cutover — the apex_habitat -> apex upgrade path. It CANNOT be
#       registered: frappe resolves patches per installed-app name (patch_handler.py
#       get_all_patches -> get_app_path(app, "patches.txt")), and a pre-rename site's
#       name is still the dead package, so it never opens this file. Registering it
#       would reach only already-canonical sites and sweep every table for nothing.
#       Operator-invoked instead, per docs/administration/identity-upgrade.md.

# and `apex.patches.v1_x.seed_demo_role_logins.execute`. Do NOT re-add either as
# an active patches.txt entry: the demo-seed gate tests (tests/test_seed_*_gate.py)
# fail if you do. Each module carries the UNREGISTERED-PATCH / COVERED-BY markers
# the registration guard requires.
#

# password as a source literal, so every checkout shared one working password. It now
# requires APEX_DEMO_PASSWORD from the operator and refuses to run unset. The literal
# is gone from the tree but REMAINS IN GIT HISTORY, so it must be treated as burned.
#
# NOT ANSWERABLE FROM SOURCE: whether any real site ever created those two accounts.
# The seeder only writes Users when developer_mode is on, and it has not been an active

# in history this repo no longer carries), so it can only have run by an explicit
# bench execute or by a migrate predating that un-wiring.

# OPERATOR ACTION, per site, in this order:
#   1. tabPatch Log for apex.patches.v1_x.seed_demo_role_logins — a row means a migrate

#      created: the developer_mode gate may have returned first. Absence of a row is
#      likewise not an all-clear, since a manual bench execute logs nothing.
#   2. tabUser for the two demo emails named in the module — this is the decisive check.
#      Present means the published password is live on that site: disable or reset.
# Until step 2 is done on a given site, those accounts are UNKNOWN, not safe.
